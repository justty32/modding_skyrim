# 調度：頂層角色與誰來做

[lessons 索引](README.md)

角色與現行選型以 [team-model](../../agentctl/docs/team-model.md) 為準。codex 2026-11-24 退役（D20，[decisions](../org/decisions.md)），工人用 Claude 系或 fsm gpt；下列原話裡「交給 codex」的部分照現行選型派給工人，「頂層不自己做」照舊。

## im-dispatcher-codex-implements
<a id="dispatcher-must-use-own-assistants"></a>
<a id="fable-top-handles-only-hardest"></a>

> 頂層是調度者：實作、調查、機械工作都派給工人或自己的助手；頂層只判斷、寫交接書、管鎖、對使用者說話，外加唯一一件最難的任務

使用者原話：

- 2026-08-21：「記住，你只是調度者，實際事情由 codex gpt sol 去做。」（當時頂層自己做完根因分析、改 Papyrus、寫報告、提交，沒有開線。）
- 2026-08-29：「beyond reach 那些，與相關的，都要下載」——頂層先自己 grep、翻庫存、比版本才寫交接書，使用者當場糾正：「**你不要自己調查，你直接委託 agent 團隊**」。
- 2026-08-30（同時跑七個團隊那輪）：

  > 我覺得你作為頂層 agent，**做太多事情了**。

  同日三次：「盡量把工作量都押給 codex gpt，sol／terra／luna 都可以。」「記住，盡量把事情都押給 codex gpt。」「盡量把工作都交給 codex。」
- 2026-08-31：「你盡量不要做事」。
- 2026-09-09：「你只負責最困難的任務」。

team-model 原句：「頂層**通常也會被允許有自己的輔助者 agent**（例如開 Sonnet 去查資料、盤點），不必事事經過團隊領導……數量使用者通常會指定，**沒指定就默認兩個**」。重申＝做得不夠、預設沒改，不是他忘了說過。

**Why:** 頂層 context 最稀缺也最貴；深潛實作把大量工具輸出灌進主對話，工人線是獨立 context、只回結論。盤點本身就是線的工作：頂層先查一輪既重複，又會把不完整的事實寫死進交接書、框住線。

**How to apply:** 拿到「去搞定 X」先想「開幾條線」，不是「我先查一下」。**瑣碎不是自己動手的理由**（2026-08-22，「刪 5 個檔＋修斷鏈＋git commit」也算）：改檔、跑 git、裝 mod、驗雜湊、寫報告、資料檔合併、逐隊驗收（跑腳本／unittest／查 ahead-behind）、調查型 diff、整批文件撰寫，一律派出去。**開場就開助手**，沒指定數量就兩個；不要等到自己開始寫腳本才想起來。

頂層只做：讀狀態、判斷、寫交接書、仲裁兩隊矛盾的宣告、資源／鎖分配、範圍裁定、對使用者說話、管領導 context；仲裁要的地面真相也叫助手探測回報。外加**唯一一件最難的任務**——跨多個 mod／層／工具鏈的推理、前一輪已失敗過、或後果不可逆；不是「我順手就能做」。開場先把待辦按難度排。

- 交接書只寫使用者要什麼、範圍（判準、禁區、驗收）、分歧怎麼選；事實（含「庫裡已有哪些版本」）由線自己查。頂層的最小查證只剩鎖狀態、現役線衝突、路徑存不存在。
- 單一有界任務直接派一個工人；只有 ① 需要同時監看 3 條以上並行線 ② 判斷是非機械的（仲裁、改判、跨線調和）兩條都成立才開領導。使用者說「開團隊」是指「別自己做」，不是「一定要配領導」。
- 別過度修正成什麼都不碰（[[dont-inflate-light-preferences]]）：判準是「這件事需要我的判斷，還是只需要有人動手」。

## fable-top-opus-middle-management

> 三層結構：頂層只做決策、鎖、瀏覽器、對使用者；讀信、巡線、收線交給管理線／領隊；工人執行。管理線用哪個模型看使用者當下怎麼說

使用者原話（依時間）：

- 2026-08-27 定三層結構：

  > 你是 fable，耗 token 很快。那些 codex 回報的時候是走 inbox，你會被喚醒去讀信。
  > 我是覺得你不要親自去讀信，你應該讓 opus 去管理這些 codex 和 inbox，然後匯報給你，
  > 你就做最終頂層決策者就好。

- 2026-08-30：「可以改成用 fable，然後讓 fable 去指揮 opus」；同日「大家都可以用 sonnet」；派工模型改定後要求「先跟管理線說，讓他們之後新派的都用這套，不然 token 消耗有點快」；同日晚「請 opus agent 去指揮 gpt-sol」。
- 2026-09-05 家中場：「我允許你帶領十個團隊，每個團隊由 opus 領導，組員可以有兩個 opus，兩個 gpt-sol，兩個 sonnet，context 由 opus 領導管理。而 opus 領導的 context 由你管理。記得每隔一些大任務後，若下個大任務差別很大或 context 達到上限的一半，那就記得 compact 他們，opus 領導對底下的組員也是。可以分一半事情給 gpt-sol 做，但順手的話還是 opus/sonnet 比較好，因爲溝通比較順暢。」

**Why:** 頂層每次被信喚醒去讀信、巡線、收線，燒的都是最貴的 context；線管理是照契約辦事（驗收條數寫死、收線步驟），不需要頂層判斷。

**How to apply:** 結構是**頂層（決策／鎖／瀏覽器／對使用者）→ 管理線／領隊（讀信、寫指示、拆工、核驗收、收線、接力派線）→ 工人**；交接書寫給管理線，由它切給工人。

- 管理線用 Fable（`Agent` 工具 `model: fable`）或 Opus 看使用者當下怎麼說，不是死規則；歷史 headcount 只限當場，今日依每線 BRIEF 的子 agent 上限，配額往下不倍增。選人做設計決策／架構規劃時 GPT 優先級較低，並非禁止。
- 派工模型一改，正在跑的管理線當場切換，不等下一輪。
- compact 判準＝大題目切換或 context 過半；頂層對領隊、領隊對成員都照做。管理線 context 吃緊時寫 STATE.md 交棒，由頂層開繼任者，不硬撐。
- 例行細節由領隊彙總，需裁示與阻塞即時上呈；頂層仍定期巡檢，不只等通知。訊息 ack 與保留依現役信箱協議。
- 對使用者說話與給他看的文件一律大白話（2026-09-05；比 [[top-level-explain-in-plain-words]] 更強：不是「順手」，是「一律」）。
