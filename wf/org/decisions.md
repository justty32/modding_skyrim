### 已定案：部門與地盤（2026-11-23）

- D1 四個部門：實體、館藏、開發、管理。
- D2 `modpack-design/` 歸館藏。館藏管「有什麼、想要什麼」，實體管「實際裝了什麼」。
- D3 只有實體能寫 MO2 的 mods 與 profile。館藏做的漢化／patch 只交「可以直接裝的包」，由實體裝、由實體驗。
- D4 遊戲鎖平時由實體發，開發要實機測試向實體借；最終權限在管理（可收回、改派、否決）。桌面鎖與其他跨部門資源由管理發。

### 已定案：管理與模型（2026-11-23）

- D5 管理部門盡量小、要最聰明；只做窗口、規矩、仲裁、收工存檔，不做內容。部門之間可直接寫信互相請求，事後知會管理。
- D6 部門主管＝eca claude、opus、effort high。
- D7 Fable 只在開發的規劃階段短暫使用，要先向管理申請。
- D8 複雜的分析／開發型內容工作（換臉、PoE 星盤、地圖移植等）不放進這四塊：未開、待規劃。
- D9 全體預設 opus，包含窗口。窗口是使用者自己開的 Claude Code CLI；要不要升 Fable 由使用者當場手動切，agent 不自己升。

### 已定案：團隊與暫存（2026-11-23）

- D10 部門底下的團隊照各部門卡的團隊節。舊功能隊：裝 mod→實體、漢化→館藏、雜事→管理書記短工、換臉→D8 未開。
- D11 暫存分三處：`wf/temp/`、`/tmp/`、`~/skyrim_mods/_staging-*`；見 [CHOICES](CHOICES.md) 第 7 題。

### 已定案：座位怎麼掛、push（2026-11-23）

- D12 部門主管有工作才用；沒事的時候可以讓它 sleep，不必 stop 或 rm。判準見 D17；效果、理由與指令見 [RUNBOOK-seats](../../agentctl/aos/RUNBOOK-seats.md)「什麼時候用哪個」。
- D13 現在不另開子 daemon：三個主管掛在 `mod_skyrim` 底下，用短名 `instance`、`library`、`dev`。agent 總數到 50 個以上就重新考慮分 daemon，所以定義與 system text 不寫 agent 名、daemon 與絕對路徑；名字與在哪台只寫在 [README](README.md) 的座位表一處。
- D14「可以隨意 push」只算 2026-11-23 本場；平時照 [user.md](../workflows/common/user.md) 要使用者當場授權。〔一次性，只算那場；見 D25〕

### 已定案：開關座位（2026-11-23）

- D15 同一場內，部門主管掛上之後的 sleep、wake、stop 由管理照 RUNBOOK 自己做、事後告知使用者。部門主管的「第一次掛上」與「移除」仍要使用者當場同意。
- D16 除了部門主管之外，部門底下的 agent 要不要移除由該部門主管處理，不用問使用者、不用問管理；事後在回信裡說開了誰、收了誰。
- D17 收工用 stop；一場之內暫時沒事用 sleep。

### 已定案：對使用者的通道（2026-11-23）

- D18 對使用者的通道預設只經窗口。例外兩個：（一）部門向管理／窗口申請權限，通過後可以寄信到使用者專區；（二）使用者有時直接寄信給部門主管（例如遊戲 crash、遊戲中的某些問題），主管直接處理並回使用者，同時知會管理。申請怎麼寫、怎麼批、效力多久見 [letters](letters.md)「對使用者的通道」。
- D19 平常時候管理部門的主管可以寄信給使用者；那位就是 `main`，不必每次申請，不另掛 `agentctl` 座位。見 [lead 卡](lead/README.md)「D19」。

### 已定案（2026-11-24）

- D20 codex 退役，工人改用 fsm gpt。
- D21 使用者直接寄給部門主管的信，不算刪檔、動 MO2、開遊戲的當場授權；維持原規矩。
- D22 已 stop 的部門主管，下一場再 `start` 不用先問使用者，管理自己做、事後告知。
- D23 D18 申請直寄流程照提案用（[letters](letters.md)）。
- D24 實體座位 `seat-instance` 帶 houseCARL 工具（`claude_mcp`）；另兩份沒說，先不帶。〔後半被 D28 取代〕

D25 起見 [decisions-2026-11b](decisions-2026-11b.md)。
