# 審查迴圈（lead 用）

回 [卡](README.md)｜[檢查清單](checklist.md)｜場地 [sites](../sites.md)

**什麼時候用**：公司場要把工具、`projects/*` 的 diff、回家單當成「做完」交出去之前（D33、D36）。使用者 2026-11-26 准把「審查 → 修正 → 複審」做成程序（「可以，去吧」）。

## 步驟

1. **寫**：施工線交 REPORT。lead 先收 commit、看測試數字，不看結論。
2. **審**：派審查代班（`line`，opus），一批一隻；工具多就按目錄切批，三批以內可同時跑。交接書寫明：審哪些 commit、原請求在哪、REPORT 寫哪、只提意見不 commit 不 `git add`、看 [檢查清單](checklist.md)。
3. **修**：審查說「要改」→ 派寫手以外的實例修。交接書固定要求：
   - 擋的必修；不擋的也修，不修寫理由。
   - 每條修正補一條先紅後綠的測試；只用合成資料與 tempdir，測試不碰真的 `~/skyrim_mods`、MO2、profile、遊戲 Data。
   - **合法輸入的輸出不能變**（家裡的黃金回歸公司跑不了）；一定會改輸出或改預設的，先做成選用旗標，交 lead 問使用者。
   - 寫入保護用白名單。
   - 同步改回家單：預期結果要跟新行為對得上。
4. **複審**：另派一隻（不是第一輪的、也不是修的），用第一輪的情境重現，確認修到、沒弄壞合法輸入、新測試換到修前碼會紅。
5. **收尾**：複審只剩不擋的小意見，便宜又跟實機安全有關的就派一條小線補，lead 自己跑測試、看 diff 核過即可，不再開第三輪審查。同一件來回 3 輪還不過 → `NEEDS-USER`（CHOICE 5）。
6. **登記**：每張回家單一行進 `agentctl/handoffs/NEXT-SESSION.md`；STATE 記「靜態通過，待回家驗」（D35）。同一類問題第二次出現，收進 [檢查清單](checklist.md)。

## commit 規矩

- **同一個 repo 同時只讓一條線 commit**（[dispatch-cli-agents](../../lessons/dispatch-cli-agents.md) 多線分工段）。平行的線分到不同 repo；同一 repo 要平行，就只讓一條線 commit，其他線只寫檔、由 lead 收，或用 `isolation: worktree`。
- 審查、複審只寫自己的 REPORT，由 lead 收進版控。
- `git add` 只加明確路徑；不 push（16:50 由 lead 統一推，D32）。
