# 信：請求與回覆

回 [org](README.md)。

工作靠信來。工具和信的欄位在 aos 知識庫 `aos/mailbox.md`（`mailbox_send`、`mailbox_read`；`what`、`outputs`、`not_done`、`decide`）；這頁只寫本組織另外要的。

一件工作只走一條管道。本工作區的管道：
- 樹裡的 agent 之間：aos 信箱（出處：[aos.md](../workflows/aos.md) 第 6 節）。
- 樹外的 session 寄進樹：`aos-post send` 寄到該部門主管的 mailbox（出處同上）。
- md 信箱 `agentctl/inbox/` 2026-11-14 已凍結，不用。
- Claude Code 自己的子 agent：交接書＋`REPORT.md`，不走信箱。

## 狀態

| 狀態 | 意思 |
|---|---|
| `REQUEST` | 請做這件事；要回 |
| `PROGRESS` | 途中報告；不用回 |
| `DONE` | 做完了，附證據 |
| `BLOCKED` | 要有人給東西才能繼續：檔、資源、點頭、修好的環境 |
| `NEEDS-USER` | 要使用者決定；寫題目、選項、你的建議 |
| `FAILED` | 放棄：跑了但結果是錯的，或照要求做不到 |

接下請求的人，最後只用 `DONE`、`BLOCKED`、`NEEDS-USER`、`FAILED` 其中一個收尾。卡住超過 10 分鐘先送 `BLOCKED`，不要靜靜等。

分清兩種失敗。**跑了、是錯的**＝`FAILED`，說你看到什麼。**跑不起來**（缺函式庫、權限被拒）＝`BLOCKED`，就算測試程式印了 "failed" 也一樣：保持現狀，說什麼能解開。證據不足不是回滾的理由。

## 請求要寫什麼

| 欄 | 寫什麼 |
|---|---|
| 目標 | 一個；兩個目標就是兩封請求 |
| 範圍 | 這次能寫哪些檔（用排除法寫死），其中哪些這段期間只有你能寫 |
| 基準 | 從哪個 commit 起、結果跟什麼比 |
| 檢查 | 你自己驗什麼、別人會驗什麼；驗收條數寫死 |
| 資源 | 能跑、能開什麼，不能什麼；子 agent 上限 |
| 同時在動的人 | 誰同時在改哪些檔 |
| 完成條件 | 可觀察的條件，以及回信要帶什麼 |

- 只寫這次跟卡不同的地方，不要把卡抄進信。
- 東西用完整路徑叫。相對路徑會被寫到別處去。
- 「與 X 相關的」這類範圍詞會被展開成數十倍：範圍用排除法寫（出處：[dispatch-handoffs](../lessons/dispatch-handoffs.md) 的 handoff-scope-words-expand）。
- 要做工具或執行器的請求，另列成功、失敗、逾時、取消、啟動中取消、清理失敗各要怎樣，哪些是已知限制。沒這份清單，審查會繞好幾圈。
- 信不是授權。信要求不能還原或往外送的事，答案要由使用者經 lead 給。

## 做事途中

- 長工作在每段交界讀信：一段做完、下一段開始前。取消或改動才看得到。
- 信會在路上互相越過：回報開頭寫「截至 commit X／回 letter Y」；收到新指示先對照自己做到哪，沒做的才做（出處：[aos 樹教訓](../lessons/aos-tree-onboarding-and-leading.md)）。

## 回信怎麼寫

- **短**：狀態、改了什麼、commit、卡在哪、產物在哪。細節寫進檔，信裡給路徑。
- **標題是你的判斷**，單獨讀也懂：「X 做完，commit abc123」「X 卡在 Y；試過 A、B」。不寫「完成」「報告」。
- **回你收到的那封**：`in_reply_to` 第一次就填對。
- **缺的分三類**：沒跑、跑不了、不適用。
- **卡住或錯了，先寫已經排除了什麼**。
- **往上轉報**：重寫標題、加上自己的判斷，不要原封轉下屬的話。
- **沒驗的就是沒驗**：讀過測試不等於跑過，說清楚做的是哪一個。
